# Устройство бота

Telegram-бот записи на экзамен по русскому языку для трудового патента.
Клиент выбирает дату, присылает паспорт и чек; администратор подтверждает
оплату и ведёт учёт через встроенную панель.

| | |
|---|---|
| Фреймворк | aiogram 3.x |
| Хранилище | SQLite + WAL, файл на смонтированном томе |
| Транспорт | long polling |
| Реплик | **1, обязательно** |
| Хостинг | Railway |
| Часовой пояс | Asia/Tashkent (UTC+5) |

## Модули

Точка входа — `main.py`. Через `AsyncExitStack` он поднимает базу, создаёт
Dispatcher с хранилищем FSM в той же SQLite, подключает роутеры и запускает
фоновый цикл. Каждый ресурс регистрирует уборку сразу после захвата, поэтому
всё закрывается и на штатной остановке, и на Ctrl+C, и на исключении посреди
старта.

|---|---:|---|
| `main.py` | 81 | Сборка Bot/Dispatcher, меню команд, запуск polling и фонового цикла, корректная остановка |
| `config.py` | 59 | Переменные окружения, ссылки на оплату, координаты, `TZ`, посев дат |
| `db.py` | 1061 | Общий коннект, схема и миграции, все запросы |

## Маршрутизация

Порядок роутеров нагружен смыслом: админский идёт первым и целиком отсечён
фильтром по ID. Апдейт от постороннего до него не доходит вообще, поэтому
проверку доступа физически негде забыть.

```
Апдейт
  ↓
LanguageMiddleware  (внутренний, на клиентском роутере)
  достаёт язык из users → data["lang"]
  ↓
router "admin"  ·  router.message.filter(IsAdmin())
  не прошёл → дальше              router.callback_query.filter(IsAdmin())
  ↓
router "client"
  последним — @router.message() без фильтров, ловит всё неразобранное
```

**Следствие.** Админ — это одновременно и клиент. Его `/start` и `/faq` должны
проваливаться сквозь админский роутер, поэтому FSM-хендлеры панели принимают
`PLAIN_TEXT` — текст без ведущего слэша. Уберёшь фильтр — команда попадёт
в название даты вместо того, чтобы сработать.

## Хендлеры клиента

17 штук. Порядок в файле = порядок проверки; хендлеры-подсказки стоят
последними и перехватывают то, что не разобрали остальные.

| Фильтр | Хендлер | Что делает |
|---|---|---|

| `lang:*` | `language_chosen` | Сохраняет язык, шлёт приветствие с кнопками «Продолжить» и «Частые вопросы» |
| `Command("faq")` | `faq_command` | Корень FAQ. **Не трогает состояние** — можно заглянуть посреди записи |
| `faq` | `faq_root` | То же по кнопке |
| `faq:s:*` | `faq_section` | Вопросы раздела + кнопки «Назад» и «Записаться» |
| `faq:q:*` | `faq_answer` | Ответ + «Назад». Для `manager` дополнительно уведомляет админов |
| `go:dates` | `show_dates` | Список дат. Если заявка уже есть — предлагает записать друга |
| `go:more` | `add_more_start` | Запись друга: спрашивает имя, минуя проверку «уже записан» |
| `waiting_applicant` + текст без `/` | `applicant_name_received` | Запоминает имя записываемого, показывает даты |
| `date_*` | `date_chosen` | Проверяет, что место есть, переводит в `waiting_passport` |
| `waiting_passport` + фото/файл | `passport_handler` | Сохраняет `file_id`, выдаёт ссылки на оплату |
| `waiting_receipt` + фото/файл | `receipt_handler` | Создаёт заявку, пересылает админам, кнопка «Записать ещё одного» |
| `confirm_*` | `confirm_payment` | Жмёт админ. Подтверждает оплату, шлёт адрес и реферальную ссылку |
| `noop` | `noop_handler` | Заглушка для кнопки «Подтвердил …» |
| `waiting_passport` | `passport_expected` | Напоминает, чего ждёт, + строка про `/faq`. Без кнопок |
| `waiting_receipt` | `receipt_expected` | То же для чека |
| — (любое) | `unexpected_message` | Вне записи: подсказка + «Частые вопросы» и «Записаться» |

с шага; про раздел напоминаем отдельной строкой.

## Пространства callback_data

Разбор идёт через `startswith`, поэтому пространства имён нельзя выбирать
наугад: **новый префикс не должен быть началом чужого**.

| Пространство | Кому принадлежит | Опасные соседи |
|---|---|---|
| `a:d…` | `a:d:` `a:dadd` `a:dbulk` `a:dhid` `a:ddate:` `a:dlim:` `a:dren:` `a:ddel:` `a:ddel1:` `a:drst:` | `a:d:` против `a:ddate:` — расходятся на 4-м символе |
| `a:b…` | `a:b:` `a:bk:` `a:bc:` `a:bc1:` `a:bo:` `a:bdoc:` `a:bdates` `a:bcast:` `a:bcast1:` | `a:b:` против `a:bo:`; `a:bc:` против `a:bcast:` |
| разделы панели | `a:menu` `a:stats` `a:export` `a:sr` `a:nudgeoff` `a:fn:` | точное сравнение, кроме `a:fn:` |
| FAQ | `faq` `faq:s:` `faq:q:` | точное `faq` — отдельным хендлером |
| поток записи | `lang:` `go:dates` `go:more` `date_` `confirm_` `noop` | — |

Добавляешь callback — проверь, что он не начинается так же, как существующий,
и допиши строку в тест маршрутизации.

## Работа с соединением

**Одно долгоживущее соединение на процесс.** Открытие файла и разбор схемы на
каждый запрос были самой дорогой частью, а FSM трогает базу на каждом апдейте.

```
PRAGMA journal_mode = WAL          читатели не блокируют писателя
PRAGMA busy_timeout = 5000         ждать блокировку, а не падать
PRAGMA synchronous = NORMAL        при WAL достаточно
PRAGMA foreign_keys = ON
create_function("pylower", ...)    регистр для кириллицы
```

Два способа получить коннект:

| | Когда | Что делает |
|---|---|---|
| `session()` | Чтение | Отдаёт общий коннект. Блокировка не нужна: рабочий поток aiosqlite и так исполняет запросы по одному |
| `writer()` | **Любая запись** | То же плюс держит `_write_lock` до конца блока |

**Под `writer()` должна идти каждая пишущая функция целиком** — вместе со своим
`commit()` и вместе с чтениями, от которых зависит запись. Иначе на общем
коннекте чужой `commit()` досрочно закроет чужую транзакцию: при
`isolation_level=None` своей транзакции у него нет, и он коммитит ту, что уже
открыта. Это не теория — так `claim_booking` закрывал транзакцию
`create_booking`, и клиент, оплативший последнее место, вместо «мест не
осталось» получал сбой, а админы не получали предупреждения.

Пропускной способности блокировка почти не стоит: рабочий поток соединения
всё равно исполняет запросы строго по одному.

## Фоновые задачи

Один `asyncio`-цикл рядом с polling, просыпается раз в час. Планировщика нет
и не нужно: от повторов защищают флаги в базе.

| Задача | Кому | Флаг | Окно |
|---|---|---|---|
| `send_due_reminders` | Подтверждённым, у кого экзамен завтра. Текст + адрес | `bookings.reminder_sent_at` | 9–21 |
| `send_abandoned_nudges` | Кто начал запись, не создал заявку и молчит > 24 ч | `nudges.user_id` | 9–21 |
| `send_cert_renewals` | У кого сертификат истекает меньше чем через 2 месяца | `bookings.cert_reminder_sent_at` | 9–21 |
| `send_backup` | Снимок базы всем админам файлом | `meta.last_backup_date` | с 4:00 |

### Доставка: `deliver()`

Общая точка отправки для всех рассылок, включая ручную из админки.
От исхода зависит, ставить ли флаг:

| Исход | Причина | Флаг | Что дальше |
|---|---|---|---|
| `SENT` | Доставлено | ставим | — |
| `BLOCKED` | Заблокировал бота, чат не найден, неизвестная ошибка | ставим | Больше не пытаемся |
| `RETRY` | 429 или сетевой сбой | **не ставим** | Ждём `retry_after`, повтор в следующий цикл |

Между отправками пауза `SEND_PAUSE = 0.04` — около 20 сообщений в секунду при
лимите Telegram примерно в 30.

### Бэкап

Снимается встроенным backup API SQLite, а не копированием файла: при WAL часть
данных лежит вне основного файла, и копия живой базы оказалась бы битой.
Операция блокирующая, поэтому уходит в `run_in_executor`.

## Подводные камни

Места, где неочевидное поведение уже стоило отладки.

**`PLAIN_TEXT` в админке.** FSM-хендлеры панели принимают текст *без ведущего
слэша*. Уберёшь фильтр — `/start` и `/faq` от админа попадут в название даты.

**Любая запись — через `writer()`.** См. [раздел про соединение](#работа-с-соединением).
Пишущая функция без блокировки ломает чужую транзакцию, причём молча.

**Время только через `db.today()`.** Всё, что связано с датами, считается по
Ташкенту. В UTC дата переключается на 5 часов позже, и вечером экзамен пропадал
бы из записи на день раньше срока. В базе при этом всё хранится в UTC.

**`DEFAULT_DATES` не для прода.** Список из конфига заполняет таблицу *только
когда она пуста*. На работающей базе он не сработает никогда — даты туда
заводятся через панель.

**Язык клиента, а не админа.** Подтверждение оплаты и отмену инициирует админ,
но получает их клиент. Язык надо брать через `db.get_user_lang(client_id)`,
а не из middleware — там лежит язык нажавшего кнопку.

**`pylower` для поиска.** Родной `LOWER()` в SQLite складывает регистр только
у латиницы. Для кириллицы зарегистрирована своя функция, иначе «алишер»
не найдёт «Алишер».

**Одна реплика — не пожелание.** Long polling ломается при двух инстансах:
Telegram отдаёт 409, апдейты делятся между ними. Плюс SQLite на томе
рассчитан на один процесс.

**Файлы WAL рядом с базой.** На томе появляются `.db-wal` и `.db-shm`.
Удалять их нельзя — часть свежих данных лежит именно там.

**Закрытие при остановке обязательно.** Рабочий поток aiosqlite не демон:
с незакрытым соединением процесс не упадёт, а повиснет. За этим следит
`AsyncExitStack` в `main()`.

|---|---|
| `BOT_TOKEN` | Токен от BotFather. **Обязательна** |
| `ADMIN_IDS` | Telegram ID через запятую или точку с запятой. **Обязательна** |
| `DB_PATH` | Путь к базе на смонтированном томе. По умолчанию `bot.db` |

Локально переменные можно положить в `.env` — `config.py` подхватит их через
`python-dotenv`, если пакет установлен. На Railway файла нет, переменные
приходят из окружения.

```bash
pip install -r requirements.txt
python main.py
```

### Тесты

```bash
python tests/smoke.py
```

Прогоняет логику базы на временном файле: лимиты и одновременные записи,
отмены, итоги экзамена, воронку, рефералов, рассылки, бэкап, полноту переводов
и совпадение плейсхолдеров между языками. Pytest не нужен, запускается как
обычный скрипт.

**Чего не хватает.** Теста маршрутизации в репозитории нет. Он проверял каждый
префикс `callback_data` через настоящий Dispatcher: куда попадает апдейт,
не течёт ли админка посторонним, работают ли `/start` и `/faq` во всех
состояниях. Без него коллизию префиксов (см.
[раздел про callback_data](#пространства-callback_data)) поймать нечем — апдейт
просто уйдёт не в тот хендлер, молча.
